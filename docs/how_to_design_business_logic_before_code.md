# Как проектировать бизнес-логику до написания кода

Этот гайд нужен для ситуаций, когда ты понимаешь, **что приложение должно делать**, но ещё не знаешь, как именно писать код.

Главная идея:

> Сначала определяем поведение системы.  
> Потом состояния, правила и переходы.  
> И только после этого выбираем Python/Django-инструменты.

Код — это способ реализовать уже принятое решение.

---

# 1. Начни не с кода, а с события

Первый вопрос:

> **Что произошло, из-за чего система вообще должна что-то сделать?**

Это можно мыслить как:

```text
EVENT
↓
CONDITION
↓
ACTION
```

Например:

```text
EVENT:
Цена товара обновилась.

CONDITION:
Текущая цена <= желаемой цены пользователя.

ACTION:
Поставить уведомление в очередь.
```

Или:

```text
EVENT:
Scheduler запустил отправку уведомлений.

CONDITION:
OutboxMessage находится в PENDING
и подписка всё ещё актуальна.

ACTION:
Отправить уведомление.
```

Если ты не понимаешь, **какое событие запускает сценарий**, код почти наверняка будет путаным.

---

# 2. Определи одну бизнес-операцию

Спроси:

> **Что именно должен делать этот UseCase?**

Не надо писать:

```text
Проверяет всё, создаёт уведомление, отправляет письмо,
обновляет подписку, обрабатывает ошибки.
```

Это уже несколько операций.

Лучше:

```text
EnqueuePriceDropNotificationUseCase
→ ставит актуальное уведомление в очередь
```

```text
SendPriceDropNotificationUseCase
→ отправляет одно сообщение из очереди
```

```text
CheckProductPriceUseCase
→ проверяет цену одного продукта
```

Полезный вопрос:

> Если я должен описать этот UseCase одним глаголом, какой это глагол?

Например:

```text
check
enqueue
send
cancel
create
update
```

Если получается несколько глаголов, возможно, UseCase делает слишком много.

---

# 3. Определи вход сценария

Спроси:

> **Что получает UseCase на вход?**

Например:

```text
Subscription
```

или:

```text
Product
```

или:

```text
OutboxMessage
```

Важно не путать:

```text
UseCase работает с одним объектом
```

и:

```text
Orchestrator получает много объектов и вызывает UseCase для каждого
```

Например:

```text
Selector
→ возвращает много Subscription

Management Command
→ перебирает их

UseCase
→ обрабатывает одну Subscription
```

---

# 4. Выпиши предусловия — Preconditions

Предусловия отвечают на вопрос:

> **Что должно быть правдой ДО выполнения сценария?**

Например для постановки уведомления:

```text
Product.status == APPROVED

Product.is_active == True

Subscription.is_active == True

Subscription.last_notified_at is None

Product.last_known_price is not None

Product.last_known_price <= Subscription.desired_price
```

Из предусловий потом обычно появляются guard clauses.

Например:

```python
if not subscription.is_active:
    raise ValueError(...)
```

Но сначала должно появиться правило:

```text
Неактивная подписка не должна участвовать в уведомлении.
```

А уже потом Python.

---

# 5. Определи результат — Postconditions

Постусловия отвечают на вопрос:

> **Что должно быть гарантированно верно ПОСЛЕ успешного выполнения?**

Например:

```text
После успешного Enqueue:

- существует один PENDING OutboxMessage;
- payload содержит актуальные данные;
- last_notified_at не изменён.
```

Это очень полезно, потому что постусловия почти напрямую превращаются в тесты.

Например:

```text
POSTCONDITION:
существует ровно один PENDING

↓

TEST:
pending_count == 1
```

---

# 6. Найди инварианты

Инвариант — это правило, которое система не должна нарушать вообще.

Спроси:

> **Что должно оставаться истинным независимо от того, какой код и откуда вызван?**

Например:

```text
У одной Subscription не может быть двух PENDING OutboxMessage.
```

Это уже не просто поведение одного UseCase.

Это правило системы.

Такие правила часто стоит защищать не только Python-кодом, но и БД:

```text
Python
→ не пытается создать дубль

Database constraint
→ физически не позволяет создать дубль
```

Пример:

```text
UNIQUE pending OutboxMessage per Subscription
```

---

# 7. Опиши состояния сущности

Если у объекта есть жизненный цикл, выпиши состояния.

Например:

```text
OutboxMessage:

PENDING
SENT
CANCELLED
```

Теперь задай вопросы:

```text
Из какого состояния можно перейти в какое?

PENDING → SENT?
PENDING → CANCELLED?
SENT → PENDING?
CANCELLED → SENT?
```

Не все переходы должны быть разрешены.

Например:

```text
PENDING → SENT        да
PENDING → CANCELLED   да
SENT → PENDING        скорее нет
SENT → CANCELLED      скорее нет
```

---

# 8. Нарисуй State Machine

Даже простая текстовая схема уже помогает:

```text
             enqueue
                │
                ▼
            PENDING
            /     \
           /       \
     отправили    стало
      успешно    неактуально
        │            │
        ▼            ▼
       SENT      CANCELLED
```

Теперь код должен реализовывать именно эти переходы.

Если в коде внезапно появляется:

```text
SENT → PENDING
```

а в схеме такого перехода нет, значит нужно остановиться и проверить логику.

---

# 9. Сделай Decision Table

Если есть несколько условий и много `if`, не пиши код сразу.

Сначала таблица.

Пример для enqueue:

| Pending существует | Подписка актуальна | Результат |
|---|---|---|
| Нет | Да | Создать PENDING |
| Да | Да | Обновить payload |
| Нет | Нет | Ничего не делать |
| Да | Нет | Не решать здесь / оставить sender |

Таблица помогает увидеть:

- все ли комбинации рассмотрены;
- нет ли противоречий;
- не выполняет ли UseCase чужую ответственность.

---

# 10. Отдельно сделай таблицу переходов состояний

Это не то же самое, что Decision Table.

Decision Table отвечает:

> Что делать при комбинации условий?

State Transition Table отвечает:

> Как меняется состояние объекта?

Например:

| Текущее состояние | Событие | Новое состояние |
|---|---|---|
| PENDING | Успешная отправка | SENT |
| PENDING | Уведомление потеряло актуальность | CANCELLED |
| PENDING | Ошибка отправки | PENDING |
| SENT | Повторный запуск sender | SENT |

---

# 11. Спроси: кто отвечает за каждый переход?

Это вопрос ответственности.

Например:

```text
Кто создаёт PENDING?
→ EnqueuePriceDropNotificationUseCase

Кто делает PENDING → SENT?
→ SendPriceDropNotificationUseCase

Кто делает PENDING → CANCELLED?
→ Sender, если перед отправкой сообщение потеряло актуальность
```

Очень полезный вопрос:

> **Какую одну бизнес-операцию представляет этот класс?**

Если ответ:

> Он и создаёт, и отправляет, и отменяет, и повторяет...

скорее всего, ответственности смешаны.

---

# 12. Проверь сценарий на изменение данных между шагами

Backend почти никогда не работает в идеальном мире.

Спроси:

> **Что может измениться между моментом A и моментом B?**

Например:

```text
19:00
создали PENDING уведомление

19:00:30
пользователь поменял desired_price

19:01
sender собирается отправить сообщение
```

Теперь вопрос:

> Можно ли доверять данным, которые были актуальны минуту назад?

Часто ответ:

```text
Нет.
Перед реальным действием нужно повторно проверить актуальность.
```

Это особенно важно для:

- уведомлений;
- платежей;
- бронирований;
- заказов;
- очередей;
- фоновых задач.

---

# 13. Проверь повторный запуск — Idempotency

Спроси:

> **Что произойдёт, если этот сценарий выполнится второй раз?**

Например:

```text
Scheduler вызвал enqueue дважды.
```

Нужно понять:

```text
Создадутся два PENDING?
или останется один?
```

Если повторный вызов не должен менять результат, это связано с идемпотентностью.

Полезный вопрос:

> Можно ли безопасно повторить эту операцию?

---

# 14. Проверь конкуренцию

Спроси:

> **Что если два процесса выполняют этот сценарий одновременно?**

Например:

```text
Process A:
видит, что PENDING нет

Process B:
тоже видит, что PENDING нет

оба создают сообщение
```

Если это опасно, одного `if` в Python недостаточно.

Может понадобиться:

```text
UniqueConstraint
F()
transaction.atomic
select_for_update
conditional UPDATE
```

Но сначала определяем проблему, а уже потом выбираем инструмент.

---

# 15. Проверь частичный сбой

Спроси:

> **Что будет, если первый шаг успешен, а второй упадёт?**

Например:

```text
email отправили ✅

last_notified_at сохранить не удалось ❌
```

Или:

```text
Product обновили ✅

PriceHistory создать не удалось ❌
```

Это помогает понять:

- нужна ли транзакция;
- где должна быть транзакционная граница;
- что вообще можно откатить;
- что нельзя откатить.

Важно:

```text
БД-транзакция может откатить БД.

БД-транзакция НЕ может откатить:
- уже отправленный email;
- HTTP-запрос;
- push;
- сообщение во внешний сервис.
```

---

# 16. Проверь boundary cases

Очень много ошибок живёт на границах.

Если правило:

```text
current_price <= desired_price
```

проверь три случая:

```text
80 < 100
100 == 100
120 > 100
```

Не только:

```text
нормальное значение
```

а:

```text
ниже
равно
выше
```

Другие типичные границы:

```text
0
1
MAX
None
пустая строка
пустой QuerySet
первая попытка
последняя попытка
```

---

# 17. Используй Given / When / Then

Это очень удобный способ превратить бизнес-правило в тест.

Шаблон:

```text
Given:
что уже есть в системе

When:
что произошло

Then:
что должно стать правдой
```

Пример:

```text
Given:
активная Subscription
Product APPROVED
last_known_price = 80
desired_price = 100
PENDING отсутствует

When:
запускается EnqueuePriceDropNotificationUseCase

Then:
создаётся один PENDING OutboxMessage
payload содержит цену 80
last_notified_at остаётся None
```

Это почти готовый тест.

---

# 18. Только теперь выбирай Django/Python-инструменты

После анализа ты можешь увидеть:

```text
Нужно:
"получить или создать"
→ get_or_create

Нужно:
"создать или обновить"
→ update_or_create

Нужно:
"один PENDING на Subscription"
→ UniqueConstraint(condition=...)

Нужно:
"несколько DB-изменений как одно"
→ transaction.atomic

Нужно:
"сравнить два поля в SQL"
→ F()

Нужно:
"загрузить ForeignKey сразу"
→ select_related
```

То есть инструмент выбирается **под уже понятное правило**.

Не наоборот.

# Пример на твоём Outbox

## Цель

Поставить уведомление о цене в очередь.

## Событие

Subscription стала подходить под условие уведомления.

## Preconditions

```text
Product APPROVED
Product active
Subscription active
last_notified_at is None
last_known_price is not None
last_known_price <= desired_price
```

## Postconditions

```text
существует один PENDING OutboxMessage
payload актуален
last_notified_at не изменён
```

## Invariant

```text
Для одной Subscription максимум один PENDING.
```

## State Machine

```text
             enqueue
                │
                ▼
            PENDING
            /     \
           /       \
        send     invalid
         │          │
         ▼          ▼
        SENT     CANCELLED
```

## Ответственность

```text
EnqueuePriceDropNotificationUseCase
→ создать / актуализировать PENDING

SendPriceDropNotificationUseCase
→ PENDING → SENT

SendPriceDropNotificationUseCase
→ PENDING → CANCELLED,
  если перед отправкой уведомление уже неактуально
```

## Повторный запуск

```text
PENDING уже есть
→ не создаём второй
→ обновляем актуальные данные
```

## Конкуренция

```text
два процесса пытаются создать PENDING
→ DB constraint не позволяет создать два
```

## Boundary cases

```text
price < desired  → подходит
price == desired → подходит
price > desired  → не подходит
```

# Главная мысль

Когда появляется задача, не начинай с:

> Какой `if` мне написать?

Начинай с:

> **Как должна вести себя система?**

Потом:

```text
поведение
↓
правила
↓
состояния
↓
переходы
↓
граничные случаи
↓
тесты
↓
код
```

Если эта последовательность понятна, код обычно становится заметно проще.

# Что делать, если программа работает сама по событию

Например, нет пользователя, который нажимает кнопки.

Программа сама должна что-то сделать:

```text
пришло событие об оплате
→ проверить данные
→ изменить статус платежа
→ пересчитать задолженность
→ сохранить результат
```

или:

```text
каждый день в 09:00
→ найти просроченные платежи
→ проверить задолженность
→ создать уведомления
```

В таком случае главное правило:

> **Не начинай с функций, классов и условий. Сначала опиши: что запускает процесс → что система делает → чем процесс заканчивается.**

---

# 1. Найди событие, которое запускает логику

Первый вопрос:

> **Почему программа вообще начала что-то делать?**

Это и есть триггер.

Например:

```text
Пришло событие PaymentReceived
```

или:

```text
Наступило 09:00
```

или:

```text
Изменился статус заявки
```

или:

```text
В очередь пришло новое сообщение
```

или:

```text
Создали новый заказ
```

Пока ты не понимаешь, **что запускает процесс**, писать его сложно.

---

# 2. Возьми один конкретный пример

Не:

> Нужно обрабатывать платежи.

А:

```text
Пришёл платёж:

credit_id = 15
amount = 5000
```

И в системе сейчас:

```text
Кредит №15

Долг: 4000 ₽
Проценты: 700 ₽
Штраф: 300 ₽
```

Теперь у тебя есть конкретные данные, с которыми можно работать.

---

# 3. Напиши системный сценарий без кода

Теперь описываем весь процесс обычным языком.

Например:

```text
Приходит событие:

PaymentReceived
credit_id = 15
amount = 5000


Система:

1. Находит кредит №15.

2. Проверяет, что кредит существует.

3. Получает текущую задолженность.

4. Определяет, куда распределить 5000 ₽.

5. Уменьшает задолженность.

6. Если задолженность полностью погашена:
   меняет статус на PAID.

7. Сохраняет изменения.

8. Завершает обработку события.
```

Это аналог пользовательского сценария из первого конспекта.

Только вместо:

```text
пользователь сделал
→ программа ответила
```

у нас:

```text
произошло событие
→ система сделала
→ получила результат
```

```text

↓

↓

↓

↓

сохранить кредит

↓

успешно завершить обработку
```

# 5. Выпиши вопросы, которые появились

Как и в пользовательском сценарии, во время описания процесса начнут появляться вопросы.

Например:

```text
Что делать, если кредит не найден?

Что делать, если amount = 0?

Можно ли получить платёж больше задолженности?

В каком порядке погашаются:
штрафы → проценты → основной долг?

Что делать, если событие пришло второй раз?

Когда именно ставить статус PAID?

Что делать, если сохранение в БД упало?
```

Вот это и есть настоящая задача.

Не:

> «Мне надо обработать событие платежа».

А конкретные решения:

```text
Если кредит не найден → ошибка.

Если сумма <= 0 → событие не обрабатываем.

Если событие уже обработано → повторно деньги не списываем.

Если остаток задолженности = 0 → статус PAID.
```

В исходном гайде преподаватель предлагает именно так вытаскивать скрытые вопросы из сценария и отвечать на каждый конкретным решением.

---

# 6. Определи вход и выход

Очень полезный вопрос:

> **Что у моей логики есть ДО запуска и что должно получиться ПОСЛЕ?**

Например.

### До

```text
credit:

status = ACTIVE
debt = 5000
```

Приходит:

```text
PaymentReceived(amount=3000)
```

### После

```text
credit:

status = ACTIVE
debt = 2000
```

Другой пример:

### До

```text
debt = 5000
```

Приходит:

```text
PaymentReceived(amount=5000)
```

### После

```text
debt = 0
status = PAID
```

Теперь задача становится гораздо конкретнее:

> Есть состояние A + событие B → получить состояние C.

---

# 7. Сделай два разных примера

Как и в исходном гайде, одного случая недостаточно. На двух примерах лучше видно, что постоянно, а где появляется ветвление.

Например:

### Случай 1

```text
Долг: 5000

Платёж: 3000

↓

Остаток: 2000
Статус: ACTIVE
```

### Случай 2

```text
Долг: 5000

Платёж: 5000

↓

Остаток: 0
Статус: PAID
```

Сразу становится видно:

```text
если debt > 0
→ ACTIVE

если debt == 0
→ PAID
```

То есть условие появилось не потому, что ты сидела и пыталась придумать `if`.

Оно появилось **из различия между двумя реальными сценариями**.

Это очень важный принцип.

---

# 8. Напиши проверки до реализации

Формат:

> произошло X → система должна сделать Y

Например:

```text
Приходит платёж 3000 при долге 5000
→ остаток 2000
→ статус ACTIVE


Приходит платёж 5000 при долге 5000
→ остаток 0
→ статус PAID


Приходит платёж 6000 при долге 5000
→ ожидаемое поведение нужно определить


Приходит платёж для неизвестного credit_id
→ ошибка


Повторно приходит уже обработанное событие
→ деньги повторно не списываются
```

Это твой список проверок.

В исходном гайде преподаватель предлагает заранее фиксировать такие проверки и не расширять задачу в процессе работы.

---

# 9. Теперь можно увидеть функции

Только теперь.

У нас было:

```text
Пришло событие

↓

найти кредит

↓

проверить данные

↓

рассчитать новый долг

↓

изменить статус

↓

сохранить
```

Из этого уже естественно появляются куски программы:

```python
credit = get_credit(credit_id)

validate_payment(payment)

apply_payment(credit, payment)

update_status(credit)

save_credit(credit)
```

Обрати внимание на порядок.

Мы НЕ делали:

```text
Так...

Наверное нужен класс PaymentService.

А ещё Repository.

А ещё PaymentProcessor.

А ещё метод handle_event()...
```

Потому что тогда ты начинаешь придумывать архитектуру раньше, чем понимаешь сам процесс.

Правильнее:

```text
сначала процесс
↓
потом ответственность каждого куска
↓
потом функции / методы / классы
```

# 10. Разделяй бизнес-логику и техническую обвязку

Допустим, задача звучит:

> При получении `PaymentReceived` пересчитать задолженность.

Здесь на самом деле есть две разные вещи.

### Техническая часть

Как мы получили событие:

```text
RabbitMQ
Kafka
HTTP
cron
файл
```

### Бизнес-логика

Что нужно сделать:

```text
получить кредит

вычесть платёж

определить новый статус
```

На этапе понимания задачи лучше сначала представить:

```python
payment_received(
    credit_id=15,
    amount=3000
)
```

И разобраться:

> Что программа должна сделать с этими значениями?

А уже потом разбираться, откуда именно пришло событие.

---

# 11. Разбивай реализацию вертикально

Не:

```text
Сначала полностью события.

Потом полностью база.

Потом полностью модели.

Потом полностью сервисы.
```

Лучше сделать один полностью работающий сценарий.

### Стадия 1

```text
Есть кредит.

Есть сумма платежа.

Уменьшаем долг.
```

Проверяем:

```text
5000 - 3000 = 2000
```

---

### Стадия 2

Добавляем изменение статуса:

```text
долг > 0
→ ACTIVE

долг = 0
→ PAID
```

---

### Стадия 3

Добавляем проверки:

```text
неизвестный кредит

некорректная сумма
```

---

### Стадия 4

Добавляем получение реального события.

---

### Стадия 5

Добавляем БД.

---

После каждой стадии должен существовать рабочий результат.

Это тот же принцип из исходного гайда: резать задачу по рабочим сценариям, а не пытаться сначала полностью построить один технический слой.

# Если логика запускается по расписанию

Например:

> Каждый день проверять просроченные кредиты.

Тогда событие:

```text
Наступило время запуска задачи.
```

Сценарий:

```text
09:00

↓

Запускается check_overdue_credits

↓

Получаем кредиты

↓

Для каждого кредита:

    дата платежа < сегодня?

        нет
        → ничего

        да
        ↓

    платёж внесён?

        да
        → ничего

        нет
        ↓

    установить OVERDUE

↓

Сохранить изменения

↓

Завершить job
```

Опять та же схема:

```text
СОБЫТИЕ
↓
ДАННЫЕ
↓
ПРОВЕРКИ
↓
ДЕЙСТВИЯ
↓
РЕЗУЛЬТАТ
```

# Если событие меняет статус

Очень удобно использовать такую запись:

```text
БЫЛО

↓

СОБЫТИЕ

↓

УСЛОВИЕ

↓

СТАЛО
```

Например:

```text
ACTIVE

↓

PaymentReceived

↓

debt == 0

↓

PAID
```

И другой сценарий:

```text
ACTIVE

↓

PaymentReceived

↓

debt > 0

↓

ACTIVE
```

Так очень хорошо видна статусная логика.

# Если событие должно породить другое событие

Добавляем ещё один шаг:

```text
Событие A

↓

проверки

↓

изменение данных

↓

новое состояние

↓

событие B
```

Например:

```text
PaymentReceived

↓

платёж полностью погасил кредит

↓

credit.status = PAID

↓

CreditClosed
```

Тогда сразу возникает следующий вопрос:

> Кто должен обработать `CreditClosed`?

Но это уже **следующий сценарий**, а не обязательно часть текущего.

# Что делать, если вообще не понимаю системную задачу

Используй этот шаблон:

```text
1. Что запускает процесс?

2. Какие данные приходят вместе с событием?

3. Какие данные уже есть в системе?

4. Что система должна проверить?

5. Что система должна изменить?

6. Что должно получиться в конце?

7. Какие есть альтернативные варианты?

8. Что считается ошибкой?

9. Может ли событие прийти повторно?

10. Какие внешние действия нужно выполнить?
```

# Две формулы, которые стоит запомнить

### Когда есть пользователь

```text
Пользователь делает X
→ система делает Y
→ пользователь получает Z
```

### Когда пользователя нет

```text
Происходит событие X
→ система проверяет Y
→ изменяет Z
→ получает новое состояние
```

То есть основная идея преподавателя остаётся той же:

> **Не пытаться сразу решить задачу «в общем виде». Сначала взять один конкретный случай и сделать понятным его поведение.**

А уже из нескольких конкретных случаев постепенно вырастут условия, функции, классы и архитектура.
